# 19:10-19:20	AIに任せられる開発基盤づくり: リポジトリ再編とE2E自動化（Bill One 開発戦略部 加藤）
- ビルワンの立ち上げからやっている
- 新卒SIer⇒2018年Sansan
- Agentic SDLC
  - ループ
  - 今回：６のリリース判断
- リポジトリの再編
  - 2026年4月時点の課題
    - 4つの部＋戦略部で合計100名
    - リポジトリがフロントエンド・バックエンド・functionsに分かれていた
      - 全部のリポジトリを個別に変更する必要がある
      - リポジトリが部を跨いで共通だから、改善しずらい
- 案3つ
  - 部ごとに1つのリポジトリ（採用）
    - それぞれの部独自で改善可能
      - 早い
      - 効果的
      - ×重複を許容するか、共通化の仕組が別途必要
  - ビルワン全部をまとめる
    - 不採用
    - 既に既存でGitHubが重い
- 改善後
  - 多くの機能開発は、1リポジトリで完結し、AIに必要十分なコンテキストを渡せる
  - 部ごとにオーナーシップを持って、作れる
  - ライブラリは、ビルワンで共通
- 残された課題
  - 部ごとに綺麗に分離できていないところもある
    - 例：システム設定画面のフロントエンド開発は複数
- E2Eテスト（2種類）
  - リグレッションテスト（2026年6月時点の課題）
    - テストケースの自動化が30％程度
- 役割分担を明確化
  - QAエンジニア
    - テストケースの妥当性
  - エンジニア
    - テストを動かす
  - 失敗件数と成功件数、実行時間
- E2Eリグレッションテストの安定性向上
  - 定期実行でエラーになった際は、AIのスキルで比較的簡単に原因究明・修正可能
  - Flakyなテストは仕組で解決する
    - 登録したものが出てくるまでにラグがあるから探せなくて失敗していた：仕組で解決
# 19:20-19:30	リスクを取りながらAIエージェントと向き合ってきた開発組織のこれまでとこれから（Bill One AR プロダクト開発部 杉田）
- ビルワンがリリースしてから1年後に入社
- ARプロダクトの副部長
  - 主な担当がビルワンの債権管理
    - フェーズ：0⇒1
      - 顧客がどんな課題を抱えているかの探索
- AIエージェントが台頭してきた流れの中で、5つの段階を踏んできた
  - AR部
    - 個人活用期
      - 6割ぐらいの人が触った
    - チーム実践記
      - 毎四半期
        - 全四半期の1.5倍成長を目指す
        - 2025年9月からは、チームでAI駆動開発のサイクルを回した
      - 目指す姿：人が考え、AIが手を動かすを標準にする
        - 移行期に一時的に生産性が落ちるのは仕方ないとチームで意思決定
    - 委任実証期
      - 単独チームで完結する案件を提供
      - 外部品質（ユーザーから見た品質）を満たせば、内部品質（コードの品質）は問わない
      - 人が見る：要件定義⇒AIに任せる⇒人が見る：確認
        - 約3倍速
      - 品質もそこまで悪くない
    - 統合期
      - 開発フローの統合
      - AIに任せる開発フローを全チーム共通に
        - 部内で共有：2026年6月
        - 取り入れ方は、各チームに委ねた
          - リーダーは決めた
      - リリース計画は、ほぼ予定通り
        - 移行期で混乱してるはずだが、とんとんの速さ
    - 上流拡張期（現在）
      - 仕様決定と意思決定の加速
      - エンジニアが決めれる範囲を広げていこうとしている
- エンジニアの仕事は、意図の設定と結果の検証に移ってきている
# 19:30-19:40	インターン4か月、AI と巨大な Bill One 開発に挑む（Bill One AR プロダクト開発部 吉村）
- 兵庫県立大学工学部工学科電気電子工学コース4回生
  - インターン（4か月）
- 自領域をカバーするだけでも精一杯なスケール感
  - コードベースで言うと50万行
- どうやって開発に参加するのか？
  - 何も知らない状態で話者が入る
  - 新卒・インターン生である話者も使っている
- まずはPBIを一周してみた
  - PBI⇒AI：調査・計画⇒話者：承認⇒AI：実装⇒
  - チームメンバーからレビューをもらって初めて気が付く
    - 実装した機能の中身やドキュメントの置き場が答えられない
  - 開発自体は、できている
  - 当時の話者のメモ
    - 傍観者じみて、ツライ
- どうすれば、話者も中に入れるか
  - 最初のPBIの流れを振り返る
    - 実装の概要しか把握できない
      - 自分にコンテキストがたまらない
    - 判断をレビューに先送り状態
      - レビューする人に負担を与えている
- 差は、知見の量という仮説
  - 知見が溜まる作業をあえて自分でやる
    - AIとペアプロをやってみようとなった
  - 手を動かして実践しながら知見を得ようというアプローチ
    - 触らない周辺のコードも目に入る
    - リサーチ
  - AIに任せられる作業も裏でやる
- 検討が必要なコードは自分で書く
  - AIがナビゲーター、自分がドライバー
  - 決まった形のコード（ControllerとかDTOとか）はAIに書いてもらう
  - 人によって変わる所を自分でやる
- 暫く実践してみて、どうだったか
  - 自分で書くので、コードがどう動くかが徐々に頭に入る
  - 気に入らないところは、書きながら直せる
  - どこになにがあるかが、だんだん分かって来る
- コスト
  - 時間はかかる
  - チームメンバーに言われたのが、こんだけAIにやるのが主流になっているからAIに振り切るのもあり
- AIの作業を並列化するための工夫
  - 1つの機能をタスクごとにPRを作る
  - worktree
    - AIが複数のherdrでworktreeを作成⇒話者が見て全部をマージする
