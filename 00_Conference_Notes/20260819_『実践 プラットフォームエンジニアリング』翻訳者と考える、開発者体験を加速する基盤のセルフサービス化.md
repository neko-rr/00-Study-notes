# 内容
- 作ったのに、使われない
  - 機能不足とは、限らない
    - 開発者が困っている事を見ずに作ると、機能が多くても選ばれない
- DevOpsとの違いを、一言で説明できない
  - DevOps
    - 開発と運用が一緒に価値を届ける文化と働き方
- 成功を、数字で説明できない
  - アウトプット＝作ったもの
  - アウトカム＝使った結果に生じた変化
  - 開発者の生産性
    - 変更リードタイムと待ち時間
- この本
  - 4名で翻訳した
  - 書籍は、3つのパート10章
    - 一貫する問いは、「開発者の仕事は、本当に良くなったか？」
  - 架空の会社の変革を10章で追体験する本
    - 何を測り、何を作り、何をやめたか
- プラットフォームエンジニアリングの定義
  - 開発者が、他チームを待たずに安全に仕事を進められる内部プロダクトを作る事
  - DevOps・SRE・開発者体験を置き換えない
- 事例
  - 業務時間の半分が調整
    - DNS,FW,ストレージ、監視の依頼で時間が消える
  - インフラ変更に最大4回のハンドオフ
    - 小さな変更でも待ち時間が積み重なる
  - デプロイを別チームが所有
  - 本番インシデントが増える
- 問題は「作業量」より「待ち時間」だった
  - 各チームの中≠組織全体
  - 全員が速くても、組織として遅くなる
- DevOpsだけでは、足りない理由
  - 理念が間違っているのではありません
  - ツールだけ導入し、責任やチーム境界を変えないと、意味がない
- ツールだけ変えると、同じ問題が戻って来る
  - 全員が全てを学ぶ代わりに、共通の～
- プラットフォームは、8つの領域で出来ている
  - 1つの巨大システムでは、ありません
- 次に、開発者が使う体験を変える
- ソフトウェア・デファインドのプロダクトとアーキテクチャ
- プロダクトデリバリーモデル
- MVPは、「機能が少ない完成品」ではない
  - 大きな間違いを小さくする仕組みだ
  - あくまでも達成するのは、機能ではなくて「仮説」
- 進化的プラットフォームアーキテクチャ
  - 最初から完成形を当てる事は、できません
    - 少数の利用者へ価値を届け、実際の利用から～
- プラットフォームエンジニアリング成功の計測
  - 利用率だけでは、成功を証明できません
    - 選択肢がない仕組ならば、利用率100％でも使いやすい訳ではない
- 2つの負荷
  - 内在的負荷
  - 外在的負荷
- 抽象化しても、メカニカルシンパシーは残す
  - 良い抽象化は、普段は隠す。必要な時は、説明できる
- 本番への経路をバリューストームで捉える
  - 測ると、待ち時間が見えて来る
    - 待ち時間を工程ごとに比べ、最も長く待つ工程を見つける
  - 測っただけでは、待ち時間は消えない
  - 人は、主観的な生き物だから、測らないと検討違いの想像をしている
- ガバナンス、コンプライアンス、信頼
- ポリシーアズコードは、ルールを自動確認する
  - ルールは文書に書くだけでは、自動承認されない
    - コードにして、いつ承認するかを決める
- 用途に合うポリシーツールを選ぶ
- 3つのテレメトリを結び付ける
  - メトリクス
- SLI/SLO/SLAとプラットフォームの責任
- 観測基盤そのものを、外から観測する
  - 監視の監視を、同じ監視に任せない
- エンジニアリングプラットフォームの構築
  - セルフサービスは、自由放任ではない
- ツールは、つながり方と運用まで見て選ぶ
- シークレットを、チケットで受け取らない
- 認証情報を作る場所を1つにする
- コントロールプレーン
- 人を足す前に、責任の範囲を見直す
- プラットフォームに完成は無い。人の仕事は、変わっていくから。
  - 成長段階によって、見る数字を変える
# Q&A
- 責任境界を明確にすることの重要性は認識しているが、難しい。また、責任範囲に閉じる事が望ましくないとお考えの場合、それを防ぐためにどのような考え方や仕組がありますか？
  - 大きな組織で、曖昧になるのは、仕方ない。それを整理するのが、プラットフォームエンジニアリングなので。
- コミュニケーションの頻度を適正化したい
  - ある程度、チャッキーな事が良い
  - 深堀りたい時に深堀れる仕組みを残す
  - 全体として、どう見られているかを設計するのが大事
