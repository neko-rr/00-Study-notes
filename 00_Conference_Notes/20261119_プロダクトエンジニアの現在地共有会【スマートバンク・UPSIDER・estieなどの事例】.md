# 「ユーザーが何を欲しいかわからない」を、VoCの仕組みで解消しにいった話
- エンジニアの価値は「How」から「Why」
  - なぜ作るのか
- ユーザーの声をテックチームまで届ける仕組みを構築した
  - 前提：支払.com　請求書の支払いをクレカでできるサービス
  - オンボーディング：新規ユーザーへの架電
  - CS：問い合わせへの対応
  - これまで：エンジニアは「改善要望」を見るだけだった
    - 生の声が見る機会が無かった
- Slackと隔週のVoC定例で、声が届く流れを整えた
  - 2つのルートで、ユーザーの声をSlackに集める
    - オンボーディング：要望に近い声を見つけたらワークフローへ
- 隔週のVoC定例で集約し、開発のバックログへ積む時間を設ける
  - 零れ落ちるものを失くす
- ユーザーの声に直接触れて、解像度が上がった
# 越境でチームはどこまで小さくできるのか？
- サービス：ワンバンク
  - お金の悩みを解決
- 越境は、当たり前になっている
- 会社が越境に積極的
  - 越境委員会を発足
    - 特定の期間にテーマに沿って活動するまとまり
    - 1チーム3人～5人いたエンジニアをどこまで少なくする事が可能か？
      - 実践・課題の探索等：1人でやり切る人も
- 越境で開発された事例が増えている
- 越境によって見えて来る課題
  - 1人で3プラットフォーム作り切る事自体は可能
  - その上で細かい仕様の把握、説明責任、意思決定が集中する
  - 場合によっては、想定以上のFatな実装に膨らんでしまう事も
  - 開発規模が大きい場合は、依然として分業が最速かつ効率的
  - スモールチーム故のコミュニケーションコストの少なさ、機敏さは享受可能
- チームの最小エンジニア人数は「2人」
  - サーバーサイド1人
  - モバイルエンジニア1人
- 専門性をチームに維持しつつ、開発の性質や規模によって、柔軟に担当を変える事が可能
- アプローチ
  - 全員が安定的に越境できるようにハーネスエンジニアリングを強化
  - 越境、スモールチーム化で主に負荷になったのが、モバイルの操作確認
- モバイルアプリのAI開発ワークフロー
  - オーケストレーター
- 会社
  - AI活用も盛んで、非エンジニアもガンガンぶん回す
  - 感想：週3東京出社(´;ω;｀)
# プロダクトエンジニアとして商談に行きまくって得た3つの知見
- 同席してヒアリング
- その場でプロダクトのデモ
- CSと一緒に、技術的な質問に回答
- 1日1回の頻度で商談に出ている
- １：作った機能は、思っていたよりずっと届いていなかった
  - 商談で見た事
    - 「○○できませんか？」と聞かれた機能が、実はすでにある
    - そんな場面が、よくある
- ２：ヒアリングよりも、「使っている人」が見えるのが大きい
  - 商談で見た事：議事録に残るのは、「要望」だけ
    - 行くと、仕事の流れや忙しさ、資料を出す相手が見える
- ３：機能より、ガバナンス・セキュリティ・稟議のほうが大変
  - 担当者は使いたいのに、会社の許可が出ない
  - LLMを使う機能は、セキュリティチェックが入ることもある
  - 商談に行って、このプロセスを一次情報として知る
# プロダクト価値を最大化するためのユーザー業務分析
- 現在は、グループ会社全体の経営情報分析システムを担当
- 「言われた通りに作ったのに、使われない」経験はありませんか？
  - リリース後：思っていたのと違う
    - ユーザーの「言葉」は聞いたけれど、ユーザーの「業務」は理解できていない
- 言葉より行動、文章より地図
  - ユーザーストーリーマッピングで業務を「1枚の地図」にする
- 事例
  - 大規模会社向けの前提は、中小規模会社でも通用するのか？
  - ユーザーストーリーマッピング活用
    - １：並べる：ユーザーの行動を時間の順に並べる
    - ２；掘り下げる：各行動の詳細・困り事を下に並べる
    - 見えてきた事
      - 大規模会社：まとめて撮影⇒まとめて検査
      - 中小規模：1回撮影してそのまま検査
